# Aloe.kg

Интернет-магазин бытовой химии и косметики в Бишкеке. Next.js 16 (App Router) + Supabase,
переписан со старого Joomla + JoomShopping.

Сайт живёт на **aloe.kg**, старый магазин остался на `old.aloe.kg`. Переезд состоялся; что
по нему ещё не закрыто — в [MIGRATION.md](MIGRATION.md).

## Запуск

```bash
npm install
npm run dev          # http://localhost:3000
```

Нужен `.env.local` с ключами Supabase и SMTP — шаблон со всеми ключами лежит в
[.env.example](.env.example), описание каждого — в
[CODEBASE.md](CODEBASE.md#environment-variables). Сами env-файлы не коммитятся.

## Окружения

Два независимых Supabase-проекта и два деплоя Vercel:

|            | адрес                             | Supabase               | `DEPLOY_ORIGIN`         | индексируется |
| ---------- | --------------------------------- | ---------------------- | ----------------------- | ------------- |
| production | `aloe.kg` (ветка `main`)          | `ukgtmxzpzprmoutqskgq` | **не выставлен**        | да            |
| staging    | `stage.aloe.kg` (ветка `staging`) | отдельный проект       | `https://stage.aloe.kg` | нет           |

Регион production — **eu-central-1 (Франкфурт)**; перенесён из ap-south-1 (Мумбай) 21 сентября
2026, порядок действий и что при этом не переезжает — [supabase/REGION-MIGRATION.md](supabase/REGION-MIGRATION.md).
Старый мумбайский проект приостановлен, не удалён.

Приостановленный проект Supabase **перестаёт разрешаться в DNS** — на бесплатном плане это
происходит само после недели без запросов, и выглядит неотличимо от удалённого. Отсюда
`.github/workflows/ping-staging.yml`: без него стейдж засыпает и роняет сборку на всех ветках.

Стейдж закрыт Vercel Authentication — открывается только из залогиненного аккаунта Vercel. Каталог
там — копия продового, **без заказов, профилей, избранного и корзин**: персональные данные клиентов
на вторую площадку не уезжают. Фотографии товаров стейдж читает из продовых публичных бакетов (строки
хранят абсолютные URL, и копировать 6000+ объектов незачем); всё, что загружено через админку
стейджа, попадает уже в его собственный бакет.

### Какой файл к какому окружению

- **`.env.local` → staging.** Его грузит `next dev`, и он же по умолчанию у `--env=stage`.
- **`.env.prod` → production.** Только для скриптов, через `--env=prod`.

Имя `.env.prod` выбрано не случайно: Next сам подхватывает `.env.production` и
`.env.production.local`, так что продовые ключи под любым из этих имён утащил бы локальный
`npm run build`, ничего не спросив.

### Скрипты обслуживания требуют `--env=`

Дефолта нет ни у одного: для бэкапа правильный дефолт — прод, для сида — никогда не прод.
`scripts/lib/target.mjs` выводит project ref из фактически загруженного URL, а не из имени файла, и
отказывается работать, если они разошлись. Запись в прод из деструктивного скрипта требует ещё и
`--i-know-this-is-production`.

```bash
npm run backup:prod        # дамп в backups/<timestamp>-prod/
npm run seed:stage         # dry run сида каталога; --execute пишет
npm run db:linked          # какой проект сейчас слинкован с supabase CLI
npm run db:push:stage      # миграции на стейдж
npm run db:push:prod       # миграции на прод
npm run db:types:prod      # types/database.ts ВСЕГДА генерируется из прода
```

### Поток веток

```
feature/* ──PR──▶ staging ──auto──▶ stage.aloe.kg  (проверка руками)
                     └────PR────▶ main ──auto──▶ aloe.kg
```

`main` защищён ruleset'ом: прямой push отклоняется, форс-push и удаление запрещены, влить можно
только через PR с зелёным джобом `verify`. Ревью не требуется (approvals = 0) — мейнтейнер один, а
собственный PR GitHub одобрить не даёт. Смысл правила не в ревью, а в том, что в прод не попадёт
код, у которого падают типы, линт, формат или тесты.

GitHub не умеет fast-forward при мерже PR, так что в `main` появится merge-коммит. Дерево при этом
идентично проверенному на стейдже — это то, ради чего раньше стоял `--ff-only`.

Миграции идут тем же маршрутом: `db:push:stage` при мерже в `staging`, `db:push:prod` после того,
как PR в `main` влит.

## Команды

```bash
npm run dev          npm run build        npm run start
npm run lint         npm run format       npm run typecheck
npm run test         # vitest, только чистые хелперы — без БД и DOM
npm run db:types     # перегенерировать types/database.ts из схемы
```

Перед пушем достаточно `npm run typecheck && npm run lint && npm test` — то же самое гоняет CI
([.github/workflows/ci.yml](.github/workflows/ci.yml)), плюс `format:check` и сборку.

## Особенности, о которые легко споткнуться

- **Оптимизация картинок Next отключена намеренно** (`images.unoptimized: true`) — квота Vercel на
  Hobby-плане. Вместо неё у каждого товара два WebP: `thumbnail_url` (≤500px) для карточек и
  `image_url` (≤1200px) для страницы товара. Не включайте обратно и не сжимайте фото сильнее.
- **`SITE_URL` жёстко равен `https://aloe.kg`** — канонический домен, на него смотрят canonical,
  sitemap и редиректы старых ссылок. Поэтому на стейдже canonical указывают на `aloe.kg`: так и
  задумано, чинить нечего. `DEPLOY_ORIGIN` — это, наоборот, адрес, на котором отвечает **этот**
  деплой: как только он отличается от `SITE_URL`, `robots.txt` отдаёт `Disallow: /`, а страницы
  носят `noindex`. Стейдж обязан её выставлять, продакшен обязан **не** выставлять — иначе магазин
  закрыт от поисковиков (см. [MIGRATION.md](MIGRATION.md)). Читается она **на сборке**, так что
  смена значения на Vercel требует передеплоя.
- **Схема БД — в `supabase/migrations/`**, а не только в дашборде. После миграции обязательно
  `npm run db:types`.
- **`/api` маршрутов нет**: данные читаются прямо в серверных компонентах, запись — через серверные
  экшены.
