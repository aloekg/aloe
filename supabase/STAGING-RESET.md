# Пересоздание стейджа с нуля

Стейдж — не бэкап и не источник истины: каталог там копия прода, покупатели и заказы выдуманы.
Поэтому его не переносят и не чинят долго — его пересоздают. Годится для любого повода: сменить
регион, разобрать испорченную схему, поднять проект вместо потерянного.

Последний раз выполнено 21 сентября 2026: `aloe-staging` (`zzyeeazpxgpfenfyxqed`) в eu-central-1,
там же, где прод. Предыдущий проект стоял в другом регионе и удалён — переносить из него было
нечего.

## Почему это дёшево

- **Дампы и restore не нужны.** Каталог кладёт `seed-staging.mjs` из свежего `npm run backup:prod`.
  Покупатели, заказы и избранное — выдумка `seed-staging-orders.mjs` с маркером `[mock]`. Настоящего
  покупателя в `auth` нет ни одного: только мок-аккаунты и свой админский, который заводится заново
  за минуту (шаг 6).
- **Копировать Storage не нужно.** Стейдж читает фотографии из **продового** бакета по абсолютным
  URL (CODEBASE.md → Environments), и сид из свежего дампа приносит их уже правильными. В
  собственном бакете стейджа лежат только тестовые загрузки через админку — их не жалко.
- **Окна и плана отката не нужно.** Простой стейджа ничего не стоит. Единственное последствие — шаг
  Build в `ci.yml` читает стейдж, и пока его нет, краснеют все ветки сразу: приостановленный или
  удалённый проект Supabase выпадает из DNS, а хост, которого нет, это не пустой ответ, а брошенный
  fetch. Отсюда правило: секреты GitHub переключаются в том же заходе, а не «потом».

**Что получаем взамен.** Миграции накатываются на пустой проект с нуля — проверка, которой не даёт
ни один другой путь: схема действительно воспроизводится из репозитория, а не только «накатывается
поверх». Baseline под это и правился руками (см. [README.md](README.md)).

## Порядок

1. **Проверить лимит проектов в организации.** На бесплатном плане активных два, и прежний стейдж
   занимает слот, пока не приостановлен или не удалён.
2. **Создать проект** в нужном регионе (сейчас — eu-central-1, там же, где прод) и вписать в
   `.env.local` его `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` и
   `SUPABASE_SERVICE_ROLE_KEY`. Ключи брать те, что реально показывает Dashboard → API Keys: у
   недавно созданных проектов это формат `sb_publishable_…` / `sb_secret_…` вместо legacy
   `anon`/`service_role` JWT. Приложение и скрипты работают с любыми. `DEPLOY_ORIGIN` в этом файле
   остаётся `http://localhost:3000` — он про локальный `next dev`, а не про стейдж.
3. **Схема:**

   ```bash
   npm run db:push:stage     # перелинкует CLI на ref из .env.local и накатит supabase/migrations/
   ```

   Поднимаются таблицы, RLS, функции и три бакета. Ничего из дашборда доносить руками не нужно —
   в этом и смысл того, что схема живёт в репозитории.

4. **Каталог:**

   ```bash
   npm run backup:prod                  # дамп прода в backups/<timestamp>-prod/
   npm run seed:stage                   # dry run: что и в каком порядке поедет
   npm run seed:stage -- --execute
   ```

   Блок `setval` из вывода — в SQL Editor нового проекта, иначе первый insert из админки столкнётся
   с существующим id. Категории сидер вставляет родителями вперёд: с FK на `categories.parent_id`
   это уже не вежливость, а требование.

5. **Заказы и мок-покупатели** (иначе `/admin/analytics` и `/admin/orders` пустые):

   ```bash
   npm run seed:stage:orders -- --execute
   ```

   Общий пароль мок-аккаунтов печатается один раз. Порядок шагов 4 и 5 обязателен: `seed-staging.mjs`
   отказывается работать, если в `orders` или `profiles` уже есть строки.

6. **Свой админский аккаунт.** Зарегистрироваться на стейдже обычным способом и выдать роль в SQL
   Editor — приложение суперадмина не назначает:

   ```sql
   update auth.users
      set raw_app_meta_data = coalesce(raw_app_meta_data, '{}'::jsonb) || '{"role":"superadmin"}'::jsonb
    where email = 'owner@example.com';
   ```

7. **Руками в дашборде нового проекта** — то, чего нет ни в миграциях, ни в `supabase/config.toml`
   (дашборд ему давно не ровня): Site URL `https://stage.aloe.kg`, redirect URLs (включая
   `http://localhost:3000`), провайдер Google OAuth, SMTP-отправитель и шаблоны писем, настройки
   подтверждения email.
8. **Vercel, стейдж-проект:** `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`,
   `SUPABASE_SERVICE_ROLE_KEY` → новый проект; `DEPLOY_ORIGIN` остаётся `https://stage.aloe.kg`.
   Дальше **redeploy**, а не рестарт: CSP (`lib/csp.ts`) вшивается в билд, и до пересборки страницы
   разрешают браузеру ходить только в старый проект.
9. **GitHub → Secrets:** `NEXT_PUBLIC_SUPABASE_URL` и `NEXT_PUBLIC_SUPABASE_ANON_KEY` — новый
   проект. Их читают и `ci.yml` (шаг Build), и `ping-staging.yml`; со старыми значениями первый
   покраснеет на всех ветках, второй будет будить мертвеца.
10. **В репозитории ref упомянут в четырёх местах:** `.env.example`, `supabase/README.md`,
    `tests/csp.test.ts` и этот файл. `package.json` и `scripts/lib/target.mjs` трогать не нужно —
    `db:link:stage` берёт ref из `.env.local`, а `PROD_REF` к стейджу отношения не имеет.
11. **Проверка:** `npm run db:linked` (ожидаем новый ref), затем на `stage.aloe.kg` — карточка
    товара (картинка приходит с продового хоста), `/search` (упрётся в `pg_trgm`), `/admin/orders` и
    `/admin/analytics` (мок-заказы на месте), загрузка фото в админке (файл падает уже в бакет
    нового стейджа), `/robots.txt` — с `Disallow: /`.
12. **Закончить `npm run db:link:prod`**, иначе следующий `db:types` прочитает стейдж. Прежний
    проект удалять только после зелёного CI на любой ветке — это и есть доказательство, что на него
    больше никто не смотрит.

## Грабли

- **Сидить можно только из полного дампа.** `backups/backup-db.mjs` не пагинировал до 21 сентября
  2026, а PostgREST режет ответ на `max_rows` молча, так что дампы старше
  `2026-09-21T08-17` содержат 1000 товаров из 3164. Сейчас скрипт падает, если собрал меньше, чем
  заявляет таблица, но старые каталоги в `backups/` так и остались обрезанными — смотрите на дату.
- **`setval` забывается легко, а проявляется поздно:** каталог сидируется с явными id, и это не
  двигает последовательности. Всё выглядит рабочим ровно до первой попытки создать товар из
  админки.
- **Мок-заказы нужны не для красоты.** Без шага 5 `/admin/analytics` на стейдже показывает «заказов
  нет» для любого периода, и проверить там нечего.

Минут двадцать, из них почти всё — ожидание готовности нового проекта.

- `db:push:stage` на пустой базе прошёл с первого раза, все двенадцать миграций подряд.
- Свежий `backup:prod` не понадобился: дамп `2026-09-21T08-17-05-757Z-prod` уже полный (3164

- Сиды: 193 бренда, 160 категорий (10 → 66 → 84), 2 баннера, 3164 товара; затем 12 мок-аккаунтов,
  150 заказов, 86 избранных, `purchase_count` поднят у 414 товаров.
- Проверено ключом anon: 2442 опубликованных товара видны, а `orders`, `profiles` и `favorites`
  отдают ноль строк при 150/12/86 в базе — RLS на месте. Картинки ведут в продовый бакет и
  отдаются `200 image/webp`; три бакета создала миграция.
